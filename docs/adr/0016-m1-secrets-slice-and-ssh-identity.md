# ADR-0016: M1 secrets slice and the instance SSH identity

- Status: Accepted
- Spec: §8.4, §9, §10, §31 M1; ADR-0003, ADR-0009

## Context

Automated SSH sessions in M1 connect as the dedicated `supermgmt` user (ADR-0009). Its key is generated by SuperMgmt rather than borrowed from the operator's agent, so it must be stored encrypted (§10). The secret store was scheduled for M2. Spec 1.4.2 moves a minimal part of it into M1 (§31) and generates the identity in both modes (§8.4). This ADR fixes what that slice contains. It introduces no new cryptography: the envelope is exactly §10 and ADR-0003.

## Decision

### The slice (`internal/secrets`)

- **`FileKeys` KEK provider** (`security.keys_dir`):
  - the directory is mode 0700;
  - each KEK is a file `<kek_id>.key`, mode 0600, a regular file owned by the daemon UID, opened with `O_NOFOLLOW`;
  - group or other bits, a symlink or a wrong owner refuses to start;
  - `.pending` files are never loaded.
- **First start:** a 32-byte KEK from `crypto/rand` with a UUIDv7 id, plus `settings.active_kek_id` and `settings.kek_check.<id>`.
- **Startup verification:** every KEK referenced by `settings` or `secrets` must pass its check record. Otherwise startup fails fast with exit 4, naming the missing ids.
- **Envelope v1:** Seal and Open with the §10 AAD labels.
- **Versioned `Store.Put/Get`:**
  - every version gets a fresh DEK;
  - lookup is by `kek_id`, so a later `rotate-master-key` rewrap (M2) is transparent.
- **`EnsureSSHIdentity`** (below).
- The `secrets` table of §9 lands in migration 000002.

### The SSH identity

- At daemon start (both modes), if `ssh/default` is absent, the `system` actor:
  - generates an Ed25519 key (`crypto/ed25519`);
  - stores the OpenSSH-format private key as secret `ssh/default` v1;
  - keeps the public key and the fingerprint in `metadata_json`;
  - emits `ssh_identity.generated`, carrying the fingerprint only.
- `GET /api/v1/ssh-key` (`config.read`) and `sm ssh-key show` print the public key.
- Nodes reference `ssh/default@<version>` through their setup metadata (ADR-0009). A future identity rotation (a new version, M2) therefore never breaks a set-up node until setup is re-run with the new key. A KEK rewrap changes no version.

### Plaintext rules

- The private key exists only in memory. It is decrypted on first use into a signer cached per `(name, version)`, and plaintext buffers are zeroed best-effort.
- It never appears in logs, events, API responses, errors or plans; it is wrapped in `audit.Secret`.
- On disk there are only KEK files (by §10 design) and the encrypted row. Tests scan the SQLite file and WAL for key bytes.

### Stays in M2

- `sm secrets import|rotate-master-key|retire-key|export-key|import-key` and the scrypt export format.
- The `secret.write` action and API, and `sm ssh-key rotate`.
- Per-node keys and provider tokens.
- KeyProvider plugins (keychain, KMS).
- Backup and restore key checks (§29.2) and the server-mode admin bootstrap.

## Consequences

- ADR-0003 becomes partially implemented in M1 (envelope and file KEKs). Its index status records that; the ADR itself is not edited.
- KEK files must be backed up separately from the database. Until export arrives in M2, losing them means regenerating the identity and re-running setup on every node. `docs/security.md` states this.
